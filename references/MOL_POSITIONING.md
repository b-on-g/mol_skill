# $mol vs React/Vue/shadcn — как корректно сравнивать

Используй этот файл когда сравниваешь $mol с другими фреймворками — в статьях, ответах на Хабре, обсуждениях экономики/найма/внедрения.

## Что НЕ писать (типичные ошибки)

### ❌ «$mol медленный старт» / «долгая настройка окружения»

**Неправда.** `npm create view-tree-lsp@latest myapp` поднимает полностью готовый проект за минуту: App, Offline, Themes, CI/CD, Prerender, Assets, Giper Baza, Tauri, Docker — всё уже сконфигурировано. У shadcn нужно ещё подключить роутер, state management, виртуализацию, i18n, темы — каждое руками.

**Как писать:** «На $mol первая страница пишется так же быстро как в shadcn — `view.tree` лаконичнее JSX. Окружение поднимается одной командой».

### ❌ «Нужен разраб именно на $mol» / «нанять некого»

**Неправда.** Подходит **любой нормальный TypeScript-разраб**, понимающий компоненты и реактивность. $mol — это TypeScript-классы + декларативный DSL над ними. Онбординг React→$mol — 2-4 недели, что меньше типового онбординга на любой новый продукт (1-3 месяца). Java→Go в РФ переучивают за 1-2 месяца, и это объективно сложнее.

**Как писать:** «На проект нужен TS-разраб, а не "специалист по $mol". Онбординг 2-4 недели — меньше, чем разобраться в чужой React-кодбазе с её Redux/Zustand/RTK/Tanstack-зоопарком».

### ❌ «Время на обучение — отдельная статья расходов»

**Неправда на горизонте проекта дольше 3-6 месяцев.** На годовом проекте время на обучение (2-4 недели) полностью нивелируется выигрышем по скорости разработки и поддержки. На React-проекте те же 2-4 недели уходят на разбирательство с архитектурными решениями предыдущего разраба и стеком из 30 npm-зависимостей.

**Как писать:** «На проекте от полугода обучение окупается. На двухлетнем — даёт чистый выигрыш».

### ❌ «Маленькое community = риск»

**Частично правда, но не критично.** Фреймворк живёт 10+ лет, репозиторий компактный, исходники читаются за дни. Claude генерирует $mol-код чище чем React из-за меньшего синтаксического шума и однозначности DSL.

**Как писать:** «Community меньше, но это компенсируется компактностью кодовой базы и хорошей генерацией LLM».

### ❌ «Платишь временем на входе» / «медленный старт и редкий стек»

Это **тот самый западный нарратив про экзотический стек**, который пользователь обоснованно режет. Не использовать.

## Что писать корректно

### Реальные минусы $mol

- **Component-экосистема меньше:** богатые datagrid'ы, charts, maps надо строить из примитивов или портировать. У shadcn 50 готовых блоков, у $mol — 150, но другого профиля (фокус на инфраструктуре: списки, формы, навигация, виртуализация).
- **Дизайн-системы из коробки:** shadcn вышел с готовым красивым набором a la Tailwind/Radix. У самого $mol дизайн нейтральный, кастомизация под брендбук — ручная. Закрывается сторонними дизайн-системами поверх стоковых компонентов, обе на $mol:
  - **BuilderUI** (`$bog_builderui_*`, [b-on-g.github.io/builderui/studio](https://b-on-g.github.io/builderui/studio/)) — shadcn-подобный набор: кнопки, карточки, диалоги, вкладки, тосты, поля, бейджи, чарты. Пресеты базы, акцента, радиуса и шрифтов переключаются в студии и подключаются одним плагином `$bog_builderui_skin`.
  - **Kit / Canvas** (`$bog_kit_*`, [b-on-g.github.io/kit/app2](https://b-on-g.github.io/kit/app2/)) — тема поверх стоковых `$mol_*` без единой рамки: слои корпус, панель, приподнятое; язык платформы iOS или Material по user agent. Подключается одним плагином `$bog_kit_shell`, рядом та же витрина в голом $mol для сравнения.
  
  Это не «дизайн из коробки», как у shadcn, а два готовых стиля, между которыми можно переключаться на одном дереве, и образец, как сделать свой.
- **Документация скуднее.** Учиться надо по исходникам и примерам.
- **Bus factor одного мейнтейнера.** Снижается тем, что код открыт и компактен.
- **Stack Overflow / документация для джунов** — хуже React.

### Реальные плюсы $mol

- **Виртуализация любой вёрстки автоматом** (не только плоских списков) — экономит недели разработки на любом проекте со списками/таблицами/комментариями.
- **Композиция через наследование DSL** — переопределяешь любое свойство любого вложенного компонента одной строкой, без форка исходника.
- **Ноль npm-зависимостей** — нет dependabot, Snyk, security-аудитов транзитивных deps. Экономия $50–150k/год на средней команде.
- **Плоский DOM** — один компонент = один DOM-узел, без div-обёрток HOC и Context.Provider.
- **Реактивность из коробки** — атомы с кэшем, persist в URL, lazy mount по умолчанию.
- **Локализация автоматом** через `@ \text` → `web.locale.*.json`.

### Когда $mol реально не подходит

- **Команда уже большая на React** — переучивать дороже чем продолжить. Стоит смотреть на $mol только для новых модулей или зелёных проектов.

## Сухой остаток для статей

Не противопоставляй $mol и React/shadcn в ключе «стартовая скорость vs производительность» — это ложная дихотомия. Корректное противопоставление:
- **shadcn:** готовый дизайн, но ручная виртуализация, форки без апдейтов, прокидывание пропсов через слои, 100+ npm-deps.
- **$mol:** компонентная композиция, виртуализация и реактивность из коробки, без зависимостей. Дизайн строишь сам, поиск разрабов через "нужен TS-разраб".
